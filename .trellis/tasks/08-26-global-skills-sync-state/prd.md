# 修复本机全局 Skills 分配与同步状态

## 目标

修复首次全局 Skills 分配后的误导状态，让用户能区分“中央库已导入”“已分配”“已同步”，并通过应用正常流程让当前电脑的 `smart-search-cli` 安装到 Claude/Codex 的正确全局目标，同时保留原有内容。

## 背景与证据

- 当前 Claude 目标只有 `.DS_Store`，Codex 正式目标不存在；两个工具均已分配 `smart-search-cli`，但没有任何 Skill managed target/item 或 baseline。中央副本与源文件一致。完整路径、只读查询与代码出处见 `research/root-cause.md`。
- P2：首次诊断要求 `desired.is_empty()`，分配后回退为 `EXTERNAL_NON_OWNED_CHANGE`，没有说明可以继续同步（`src-tauri/src/skills/service.rs:405`、`:412`）。通用算法对此场景允许合并，不能把它当成故障或覆盖授权（`src-tauri/src/sync/mod.rs:412`）。
- P2：分配按钮只更新中央意图，成功后仅刷新查询，按钮附近缺少尚需预览/应用的提示（`src/features/skills/skills-page.tsx:103`、`:363`）。
- Codex 正式用户目标 `~/.agents/skills` 符合官方约定，不需要改成兼容导入来源 `~/.codex/skills`。

## 需求

### R1：准确显示首次待同步

当已有分配、中央副本正常、目标尚未形成受管基线且没有实际冲突时，Claude/Codex 全局卡片应显示“已分配，待同步”，而不是让用户以为导入损坏。覆盖目标缺失、空目录、只有元文件或含不同名外部条目等情况；明确下一步为预览并确认应用。

### R2：明确分配不等于同步

分配区及成功反馈说明分配只改变中央配置。导入、分配、取消分配都不自动执行原生写入；真正应用仍消费用户明确预览的计划。状态与列表在分配后一起刷新。

### R3：保留安全保护与兼容性

同名外部目录/未知或损坏链接、中央副本损坏、受管漂移、半基线、权限/类型/策略问题不得显示成正常待同步。已有完整基线后的真实非受管变化保持原诊断。保留 `.DS_Store` 和其它未知内容，不把它们作为技能数量。其它资源与 MCP 的状态语义不变。

### R4：完成当前电脑的单 Skill 同步

实施获批后，仅通过应用现有预览/应用流程，为 `smart-search-cli` 同步 Claude 和 Codex 两个全局目标，核验链接、应用状态和管理记录。原来源、中央副本、Codex 内置技能以及其它配置保持不变。实际预览若超出此范围或出现冲突，停止并报告，不执行强制覆盖。

- [x] AC1（R1）：两个工具的首次目标矩阵均显示准确待同步说明；仅创建过预览记录但无 baseline 的情况一致。
- [x] AC2（R2）：分配后可见明确下一步，列表与目标状态刷新；测试证明没有隐式 preview/Apply。
- [x] AC3（R3）：真实冲突、受管变化、半基线、中央损坏和策略/权限错误仍按原规则阻断，已有基线的非受管漂移不被覆盖，MCP 回归通过。
- [x] AC4（R1、R3）：隔离环境复现本机 `.DS_Store`/缺失目录组合，分别预览并应用后，链接正确、原有条目不变、目标显示已同步。
- [x] AC5（R4）：本机两个工具的 `smart-search-cli` 链接及 Skill baseline/managed item 与中央副本一致；分别记录实际成功与验证边界，不把 mock 或静态检查当作真实桌面验收。

## 范围外

- 不改变导入为自动接管/同步，不批量迁移 Skills，不修改凭证、MCP、Provider、Prompt 或插件配置。
- 不改 Codex 正式目标路径，不删除 `.DS_Store` 或内置集合来消除状态提示。
- 不执行技能正文、脚本或模型请求，不扩展到技能自身 CLI/服务依赖诊断。
- 不重构通用漂移/同步引擎，不扩展已有完整 baseline 后的全部分配差异建模。
